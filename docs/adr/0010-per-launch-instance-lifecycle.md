# Instance lifecycle bound to one launch

For the subprocess host and generated settings, see [ADR-0005](0005-subprocess-host-with-generated-settings.md).

## Context

The instance is defined as "the runtime directory generated for one Pi process", but the implementation once pinned it to `instances/<profile>/agent`, reusing the same path on every launch of the same profile. Three consequences coexisted: concurrent launches of the same profile rewrote each other's managed files and `pid`; in-session switching could only rewrite in place (`PI_CODING_AGENT_DIR` cannot change inside a process), leaving the directory name inconsistent with its content after a switch; and directory reuse accidentally conferred persistence on "third-party state created at runtime", so pi-subagents' mission store was replicated into mutually unrelated per-profile copies.

Instance content falls into three classes: managed files generated by pi-profile, symlinks into the real agentDir, and **entries created inside the instance at runtime**. The third class is not part of the mirror snapshot and previously survived only thanks to directory reuse.

## Decision

The instance directory is bound to one launch: each launch generates a unique directory `instances/launch-<random id>`, which is the agentDir handed to Pi; paths are never reused for the same profile. Reclamation is handled by the startup sweep, with no deletion at exit:

| Determination | Outcome |
| --- | --- |
| `pid` parseable and process alive (including present but unsignalable) | Keep |
| `pid` parseable and process gone | Reclaim |
| `pid` missing or unparseable, mtime beyond the grace period | Reclaim |
| Directory contains entries not generated by pi-profile | Keep and warn |
| Directory not in `launch-` form | Not deleted |

State created at runtime is anchored back to the real agentDir with symlinks: directories (`sessions`, `missions`) are created under the real agentDir when missing; files (`auth.json`, `models-store.json`) get **dangling-tolerant** symlinks inside the instance — the target is "the path where this file would be created in the real agentDir", Pi sees it as absent and writes through the link, and the file's content and format remain owned by Pi. When judging "unrecognized entries", the real agentDir is **not** consulted; only whether the entry itself was generated by pi-profile matters.

## Rejected alternatives

**Persistent per-profile directories.** Concurrent launches of the same profile would share one directory, and in-session switching would rewrite files another live session is using; the directory name would stop matching its content after a switch. "Replacing the whole directory each time" does not save it — the conflict comes from the shared path itself.

**Absorbing on reclaim** (moving unrecognized entries into the real agentDir). Third-party records embed absolute paths into the instance: pi-subagents' ledger `recordPath`, records' `ownerSessionId`, and artifact paths. After a move, the ledger treats those pointers as stale and clears them; fixing that would mean rewriting third-party file formats plus a conflict-merge strategy.

**Pointing `missions` at the project `.pi/subagents/missions`.** The launcher would create files on behalf of the project — even for untrusted projects — breaking the trust gate, and violating pi-subagents' choice to keep the store in agentDir to keep workspaces clean.

**Enumerating more third-party state directories into the seed list.** The list is compatibility debt: when an extension changes paths, the seed fails silently, and silent failure is the least acceptable outcome. Only entries with observed evidence are admitted; unlisted ones are caught by the "unrecognized entry" warning.

**Pre-creating state files with Pi's empty values** (writing `{}` to `auth.json`, `models-store.json`). Locks would land on the real paths, which looks cleaner, but it hardcodes Pi's internal empty-value shape: when Pi later changes format without rewriting existing files, a stale file is left behind. The symlink approach lets Pi own the file content and format forever.

**Deleting instance directories at exit.** Every exit path terminates the pid, so the next launch's sweep always converges; moving deletion onto the exit path buys immediate tidiness at the cost of deletion logic on signal paths.

## Consequences

- Unrecognized-entry determination keeps dead directories and re-warns on every launch until the user acts; this is deliberate — better kept and reported than silently destroying third-party data.
- The seed list silently goes stale when third parties change paths; the warning above is the only thing that turns it into a visible failure.
- File seeds use dangling symlinks, so locks land next to the symlink path (`<instance>/auth.json.lock`), and concurrent instances do not serialize writes to the same real file; in exchange we never hardcode Pi's file format.
- `sessions` and `missions` are created under the real agentDir (native Pi creates them too), so this state is shared across profiles rather than isolated.
- Legacy 0.4.x `instances/<profile>/agent` directories are neither cleaned nor migrated; the mission records inside carry old absolute paths and can only be disposed of by the user.
- PID reuse can temporarily keep a directory that should have been reclaimed, until that pid exits.
